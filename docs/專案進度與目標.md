## 一、專案目標（給組員的一頁說明）

### 我們在做什麼？

**ScamSentinel** 是台灣情境下的**行動安全雙代理系統**：使用者把可疑簡訊、通知或連結送審，系統回傳**可解釋的風險分數與建議**；同時也能像任務導向助理一樣追問、搜尋、開連結。

核心分工：

| 代理 | 全名 | 角色 |
|------|------|------|
| **CAI** | Chat Agent Intelligence | 對話主控：理解意圖、規劃任務、呼叫工具、整理回覆 |
| **DAI** | Defense Agent Intelligence | 安全審核：風險評分、個人化情境、產出風險卡與 Narrator 說明 |

一句話：**CAI 負責「怎麼幫使用者」；DAI 負責「這則內容安不安全、對這個人有多危險」。**

### 目前專注在做什麼？（2026-08）

近期主線是把**簡訊防詐**做成可 Demo、可解釋、可個人化的完整體驗，涵蓋後端、桌面與 Android App。

### 送審時實際發生什麼？

```
使用者貼簡訊（App 或桌面）
    │
    ▼
CAI：載入人設 + Memory → call_dai
    │
    ▼
DAI dual_path_analyze
    ├─ 推斷關係／管道（LLM + 規則 + 人設先驗）
    ├─ Path A：ML 威脅分 + GNN 情境分
    ├─ Path B：LLM 獨立對照（可關：`DAI_DUAL_PATH_B=0`）
    └─ Narrator：用人話說明分數依據（可關：`DAI_DUAL_NARRATOR=0`）
    │
    ▼
風險卡：威脅／情境並列 + Narrator 報告 → CAI Replan 整理回覆
```

### ML 評分引擎（桌面 `ml` 專案）

DAI 的 Path A 分數來自**獨立的 ML 研究專案**（路徑：`C:\Users\labpc\Desktop\ml`），產品名同為 **ScamSentinel**。核心命題：

> 不只問「像不像詐騙」，更要問「**對這位使用者**有多危險？」

| 面向 | 問題 | 技術 | 產出 |
|------|------|------|------|
| **Threat（威脅）** | 事件本身有多危險？ | XGBoost（`scam_type`）+ LR（`threat_score`） | 話術、載荷、意圖等結構化特徵 |
| **Context（情境）** | 對此人是否合理／易受害？ | HeteroGNN（Context Graph）+ 規則 fallback | 年齡、職業、關係、管道、熟悉度 |

**定案：兩分並列輸出，不做加權融合**；產品閘道分僅取 `max(threat, context)` 供 CAI 動作門檻。

### 架構原則（全員需遵守）

- **CAI** 為任務主控，**不直接寫入**底層公司資料庫。
- **DAI** 為安全審核、知識入庫、唯讀檢索的**唯一受控入口**。
- **寫入**公司記憶：僅 `secure_ingest`（規劃中）。
- **讀取**：`call_dai` → `guarded_retrieval` / `guarded_org_lookup`（規劃中）。
- **網路 raw data** 一律先經 DAI 消毒／審核後才可入庫或回傳正文。
- **評分原則**：機器證據為主（Path A）；LLM 補語意與人話（Path B、Narrator），**不讓 LLM 單獨決定最終分數**。

```
使用者（員工）
    │
    ▼
Ingress 正規化 ──► Memory / Context Pack
    │
    ▼
Planner LLM ──► Todo 佇列 ──► Executor（每次 todos[0]）
    │                              │
    │                    ┌─────────┴─────────┐
    │                    ▼                   ▼
    │              CAI 技能            call_dai → DAI
    │         search_web / weather   防詐 DAG / 未來：知識·組織檢索
    │         open_url / fetch_url
    │                    │
    └──────────── Replan LLM ◄────────┘
                        │
                        ▼
                  Final Answer
```

|------|------|------|
| CAI | `dual_agent/cai/` | Planner、Executor、Replan、Ingress 校正、個人記憶 |

| 共用 | `dual_agent/ingress.py` | 輸入分類（意圖／待審正文／動作指令） |

## 五、已知問題

### 5.1 情境分常為 0（設計行為，非壞掉）

當推斷為 **Official 關係 + 熟悉管道（如 SMS 在常用清單）** 時，Path A 的 `context_score` 會壓到接近 0——代表「對這組人設沒有額外情境加成」，**威脅分仍可能很高**，閘道分取 `max(threat, context)` 擋下高風險。

Narrator 會依人設四欄說明為何情境分低；若需「高威脅＋自稱官方」也抬高情境分，需另加規則或重訓（見 [RISK_SCORING.md](./RISK_SCORING.md)）。

### 5.2 其他限制

- Executor 每次只跑 `todos[0]`，多步任務依賴 Replan 接續。
- `MAX_EXECUTOR_STEPS` 預設 3、`MAX_REPLAN_ITERATIONS` 預設 5。
- 多步 todo 整合測試仍不足。

### MVP 驗收標準

1. 兩位不同 `employee_id` 對話記憶互不干擾。
2. 可問「XX 部門主管是誰」（組織圖）。
3. 文件入庫後可依權限 RAG 問答。
4. 簡訊仍出風險卡；工作指令不誤觸防詐。
5. 寫入僅 `secure_ingest`；CAI 不直寫公司圖譜 DB。
