## 一、目的與範圍

本計畫針對 Dual-agent 中**所有與「理解使用者意圖／訊息語意」相關的模組**，提出分階段改善路線。語意分析在本專案分兩條主線，職責不同、不可混用：

| 主線 | 模組 | 職責 | 輸出 |
|------|------|------|------|
| **CAI 意圖路由** | Ingress、`ingress_router`、`semantic_router`、Planner validate | 判斷使用者要做什麼（搜尋、開連結、送審、閒聊／元問題） | `task_type`、`todos`、是否 `call_dai` |
| **DAI 語意補充** | `semantic_llm`、`semantic_supplement`、融合層 `semantic_floor` | 在機器證據之上補台灣詐騙框架（H）與語言品質（I） | `tier_h`、`tier_i`、`labels`、`r_llm_optional` |

**不在本計畫首輪範圍**：組織圖譜 RAG、公司知識入庫、`guarded_retrieval`（見專案 Phase 2–3）。

**設計原則**（對齊 [AGENTS.md](../AGENTS.md)）：

- 規則與 LLM **分層**：高信心、可稽核的規則優先；低信心才交 LLM。
- 不做向後相容層：舊 regex 或 prompt 若被取代，直接刪除而非疊加 fallback。
- 每階段交付**可端到端驗證**的增量，不為未完成抽象犧牲現有可用流程。

## 二、現況盤點

### 2.1 CAI 意圖路由

```
使用者輸入
    │
    ├─► Ingress（L0 規則：簡訊分享、純 URL、審查意圖…）
    │       └─► ingress_router（L1 LLM，可 mock）
    │
    ▼
Planner LLM → validate_planner_output
    │
    └─► semantic_router（L2 規則：複合句切分、skill 選擇）
            confidence=high → 覆寫 todos
            confidence=low/none → 交回原 Planner 結果
```

| 元件 | 位置 | 現況 |
|------|------|------|
| Ingress L0 | `dual_agent/ingress.py` | 簡訊、審查、URL 等硬規則已落地 |
| Ingress L1 | `dual_agent/cai/ingress_router/` | LLM 路由 + `guard_route_decision` 護欄 |
| Semantic Router | `dual_agent/cai/semantic_router.py` | **純 regex**；黃金測試集覆蓋複合句、假設問句、送審 |
| Planner 整合 | `planner_llm.py` | validate 後呼叫 `apply_semantic_router` |
| 測試 | `tests/test_semantic_router.py`、`test_ingress_intent_router.py` | 多為 mock／無 Ollama |

### 2.2 DAI 語意補充

```
正文 + component_scores
    │
    ▼
semantic_supplement（DAG 第 6 步）
    │
    ├─► semantic_llm：tier_h (0–20)、tier_i (0–12)、labels、人話摘要
    ├─► urgency_only 護欄：無 Tier1/2 機器證據時壓低加分
    │
    ▼
fuse_risk_score_weighted（機器 65% + 語意 35%）
    │
    └─► semantic_floor_from_labels：依 labels 抬高 risk_score 下限
```

| 元件 | 位置 | 現況 |
|------|------|------|
| 語意 LLM | `dual_agent/dai/risk_analysis/semantic_llm.py` | Ollama JSON；可 `DAI_SEMANTIC_LLM=0` 關閉 |
| 標籤下限 | `verdict.py` | 人工表（phishing→60、malicious_link→55…） |
| ML 路線 | [DAI_ML風險校準.md](./DAI_ML風險校準.md) | **labels 尚未系統化為 ML 特徵**；融合權重為工程先驗 |
| Threat Intel / TLS | 占位 | 機器層證據不足時，語意層負擔偏高 |

## 三、已知問題與根因

### 3.1 CAI 意圖路由

| # | 問題 | 根因 | 嚴重度 |
|---|------|------|--------|
| 1 | 元問題誤觸 `search_web`（如「你怎麼在搜尋網頁」） | 關鍵字「搜尋」觸發 `explicit_web_search_requested` | 中（部分已修：`meta_question_about_assistant_behavior`） |
| 2 | 單字或極短句（如「你」）誤排工具 | 缺乏 `direct_response` 短路；Planner LLM 不穩定 | 中 |
| 3 | `semantic_router` `confidence=low` 頻繁交回 LLM | regex 覆蓋不足（口語變體、英文混用、省略主語） | 中 |
| 4 | 指代詞句（「剛剛那個」「我喜歡的遊戲」）無法路由 | 刻意標記 `deictic_needs_context`，但無後續記憶銜接策略 | 低 |
| 5 | mock 管線與真實 Planner 路徑不一致 | 測試時 semantic_router 覆寫未走完整 E2E | 低（測試缺口） |

### 3.2 DAI 語意補充

| # | 問題 | 根因 | 嚴重度 |
|---|------|------|--------|
| 1 | 融合權重（65%/35%）未校準 | 無標註資料集 | 高（準確性） |
| 2 | `labels` 與 `semantic_floor` 雙軌邏輯 | labels 抬高下限但未進 ML 特徵向量 | 中 |
| 3 | TI/TLS 占位時語意層權重過重 | 機器證據為 0，LLM 成主要訊號 | 高 |
| 4 | 語意層輸出穩定性 | 依單次 LLM JSON；無結構化校準集 | 中 |
| 5 | 台灣話術覆蓋未知 | 缺乏持續更新的詐騙語料與回歸測試 | 中 |

```
Phase 0  度量基線 ──► Phase 1  CAI 意圖 ──► Phase 2  DAI 語意 ──► Phase 3  跨層整合

```

## 六、Phase 1：CAI 意圖路由改善

**目標**：減少 Planner LLM 誤排工具；高信心規則覆蓋常見任務句型。

### 6.1 L0/L1 Ingress 強化

| 工作項 | 做法 |
|--------|------|
| 元問題／能力詢問短路 | 擴充 `meta_assistant_or_chat_scope` 模式；Ingress 與 validate **同一套** taxonomy |
| 極短句處理 | ≤2 字且無 URL → `direct_response`，不進 Planner 工具路徑 |
| L0 優先於 L1 | 維持現有 phishing L0 override；補文件說明優先序 |

### 6.2 Semantic Router v2（規則層）

| 工作項 | 做法 |
|--------|------|
| 子句切分 | 擴充連接詞（「還有」「另外」「順道」）；支援全形／半形 |
| skill 覆蓋 | 補 `instant_answer` 觸發（「是什麼」「幾點」「多少」+ 實體） |
| 低信心降級策略 | `confidence=low` 時記錄 `reason_codes` 至 pipeline progress，供後續 LLM 微調 |
| 刪除重複邏輯 | 與 `planner_validate`、`ingress` 重疊的 regex **合併到單一模組**，避免三處各寫一套 |

**建議模組結構**（不破壞現有 import 路徑的前提下內部分拆）：

```
dual_agent/cai/intent/
├── patterns.py      # 共用 regex／觸發詞
├── ingress_rules.py # Ingress L0
├── router_rules.py  # semantic_router 規則
└── taxonomy.py      # 與 task_taxonomy 對齊的意圖枚舉
```

### 6.3 Semantic Router v3（選配 LLM 層）

僅在 **規則 confidence=low** 時呼叫輕量 LLM（與 `ingress_router` 共用 schema）：

- 輸入：user_text + session 摘要（最近一輪）
- 輸出：`IngressRouteDecision` 相容結構
- 護欄：`guard_route_decision` 不允許 LLM 繞過 L0 送審／phishing 規則

### 6.4 驗收標準

- [ ] CAI 黃金集路由準確率 ≥ **95%**（mock 管線）
- [ ] 元問題誤觸 `search_web` 率 = **0**（回歸 `meta_誤觸搜尋` 劇本）
- [ ] 複合句（天氣 + 開連結）維持現有黃金測試全綠

## 七、Phase 2：DAI 語意層改善

**目標**：語意層**可稽核、可回歸**；在機器證據不足時不過度抬分。

### 7.1 結構化輸出與護欄

| 工作項 | 做法 |
|--------|------|
| 標準 labels 枚舉 | 將 `semantic_llm` prompt 中的 labels 抽成 `SemanticLabel` 常數表，與 `semantic_floor` 表 **單一來源** |
| 機器證據門控 | 當 `max(r_rules, r_threat_intel, r_tls, r_toxic_fused) < 閾值` 時，cap `r_llm_optional`（現有 urgency_only 邏輯泛化） |
| quotes 稽核 | `quotes` 欄位必須是正文子字串；不符則丟棄該 quote |
| 離線 replay | `semantic_supplement` 可單步重跑，輸出 diff 報告 |

### 7.2 Prompt 與話術庫

| 工作項 | 做法 |
|--------|------|
| 台灣詐騙框架 H | 按類別維護話術範例（政府補助、物流、銀行、投資、OTP）嵌入 few-shot |
| 語言品質 I | 繁簡混用、錯字群聚的明確評分 rubric（0 / 4 / 8 / 12） |
| 版本化 | `SEMANTIC_PROMPT_VERSION` 環境變數；變更 prompt 須更新回歸集預期 |

### 7.3 與 ML 路線銜接

對齊 [DAI_ML風險校準.md](./DAI_ML風險校準.md) Phase 0–1：

| 工作項 | 做法 |
|--------|------|
| labels → 特徵 | `feature_extractor.py` 增加 label one-hot |
| 雙模式切換 | `ml_*` 模式停用 `semantic_floor`（避免與 ML 雙重抬分） |
| 訓練資料 | semantic replay 產出的特徵矩陣併入 bootstrap 資料集 |

### 7.4 驗收標準

- [ ] DAI 語意回歸集：label 命中率 ≥ **85%**（允許邊界案例人工標記）
- [ ] 正常簡訊（非詐騙）`r_llm_optional` 中位數 ≤ **8**
- [ ] 高風險話術（OTP／匯款）`semantic_floor` 或 label 下限觸發率 ≥ **90%**

## 八、Phase 3：跨層整合與長期演進

**目標**：CAI 意圖與 DAI 語意共用 taxonomy；端到端可追蹤。

### 8.1 共用意圖／風險 taxonomy

| 概念 | CAI | DAI |
|------|-----|-----|
| `check` / 送審 | Ingress、`call_dai` | 完整 DAG |
| `hypothetical_risk` | `direct_response` + 可選輕量 DAI | 簡化評分路徑（未來） |
| `malicious_link` 等 label | Planner 不開連結 | 阻擋／追問建議 |

建立 `dual_agent/shared/intent_risk_taxonomy.py`（或擴充 `task_taxonomy`），Ingress、semantic_router、semantic_llm 引用同一枚舉。

### 8.2 指代與多輪上下文

- CAI：`deictic_needs_context` → Memory 提供上一輪 artifact／URL
- DAI：送審正文與使用者追問分離存入 `payload`，語意層只看 artifact

### 8.3 Threat Intel / TLS 接入後重平衡

TI/TLS 上線後重新跑 Phase 0 基線，**下調** `DAI_R_LLM_WEIGHT` 預設值（語意層不再補機器缺口）。

### 8.4 驗收標準

- [ ] 端到端劇本（`agent_full_coverage`）全綠
- [ ] ML LR 模型（若 Phase 1 完成）validation AUC ≥ 基線 + **0.05**
- [ ] 風險卡 `explanation` 使用者可讀性人工抽樣滿意度 ≥ **80%**

## 十、風險與依賴

| 風險 | 影響 | 緩解 |
|------|------|------|
| Ollama 模型輸出 JSON 不穩定 | DAI 語意層、Ingress L1 失敗 | 規則護欄 + `llm_json` 修復；溫度 0 |
| 無標註資料 | ML 校準延後 | Phase 0 bootstrap + 合成語料（已有 `bootstrap_synthetic_labels.py`） |
| regex 與 LLM 邏輯分散 | 維護成本高 | Phase 1 合併 `intent/` 模組 |
| TI/TLS 長期占位 | 語意層過重 | Phase 2 門控 + Phase 3 重平衡 |

**外部依賴**：

- Ollama 本地模型（Planner、semantic_llm、ingress_router）
- 未來：VT / 165 Threat Intel API（見 [FISHBONE.md](./FISHBONE.md)）
