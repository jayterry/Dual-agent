## 一、目的與範圍

本計畫針對 Dual-agent 中**所有與「理解使用者意圖／訊息語意」相關的模組**，提出分階段改善路線。語意分析在本專案分兩條主線，職責不同、不可混用：

| 主線 | 模組 | 職責 | 輸出 |
|------|------|------|------|
| **CAI 意圖路由** | Ingress、`ingress_router`、`semantic_router`、Planner validate | 判斷使用者要做什麼（搜尋、開連結、送審、閒聊／元問題） | `task_type`、`todos`、是否 `call_dai` |
| **DAI 語意補充** | `semantic_llm`、`semantic_supplement`、融合層 `semantic_floor` | 在機器證據之上補台灣詐騙框架（H）與語言品質（I） | `tier_h`、`tier_i`、`labels`、`r_llm_optional` |

**不在本計畫首輪範圍**：組織圖譜 RAG、公司知識入庫、`guarded_retrieval`（見專案 Phase 2–3）。

**設計原則**（對齊 [AGENTS.md](../AGENTS.md)）：

- 規則與 LLM **分層**：高信心、可稽核的規則優先；低信心才交 LLM。
- 不做向後相容層：舊 regex 或 prompt 若被取代，直接刪除而非疊加 fallback。
- 每階段交付**可端到端驗證**的增量，不為未完成抽象犧牲現有可用流程。

### 1.1 DAI 風險融合：雙路線定案（維持不變）

DAI 風險評分**維持雙路線並行**，不互相取代；共用規則底線與機器層，融合層依 `DAI_RISK_FUSION_MODE` 切換。

| 路線 | 模式鍵（規劃） | 語意／校準來源 | 狀態 |
|------|----------------|----------------|------|
| **A. Legacy** | `legacy` | 人工權重 + `semantic_llm`（H/I、labels） | 已實作，預設 |
| **B. LLM 語意路線** | `enhanced_embed`（規劃） | **KEA + TAPE + 文本增強嵌入**（§4.4） | 規劃中，**本計畫 LLM 主交付** |
| **C. ML 校準路線** | `ml_lr` / `ml_rf` | `feature_extractor` + LR／RF | 規劃中，見 [DAI_ML風險校準.md](./DAI_ML風險校準.md) |

```
                    ┌─ Route B：KEA/TAPE → enhanced_text → embed → r_embed
                    │
正文 + 機器層 ──► 規則底線 ──┼─ Route A：semantic_llm（過渡）→ legacy 融合
                    │
                    └─ Route C：KEA/TAPE 特徵 + embed 特徵 → LR/RF → p_fraud
```

**定案**：

- **LLM 那條**必須做到 **KEA（知識增強）+ TAPE（威脅解釋）+ 增強文本嵌入**，不再以「僅 H/I labels」為長期終點。
- **ML 那條**維持原計畫（標註 → 特徵 → LR/RF）；日後可吃 Route B 產出的 KEA/TAPE／嵌入特徵。
- 兩路以 **shadow 對照** 上線；`legacy` 始終可回退。

## 四、改善策略總覽

採**四階段、每階可獨立驗收**：

```
Phase 0  度量基線 ──► Phase 1  CAI 意圖 ──► Phase 2  DAI 語意 ──► Phase 3  跨層整合
   │                      │                      │                      │
   │                      │                      │                      └─ ML 校準、labels→特徵
   │                      │                      └─ 結構化輸出、護欄強化
   │                      └─ Embedding 意圖 + 規則 + 選配 LLM
   └─ 黃金語料集、審計腳本、指標儀表
```

**CAI 意圖路由分層（目標架構）：**

```
使用者輸入
    │
    ▼
L0  Ingress 硬規則（phishing、純 URL、簡訊分享…）     ← 安全優先，零 token
    │
    ▼
L0.5 Embedding 意圖比對（範例句 → skill 類型）     ← §4.3，本計畫核心改善之一
    │   命中工具意圖 → 交 regex 抽參數
    │   命中閒聊／元問題 → direct_response
    │   皆未命中 → 視為閒聊（direct_response）
    │
    ▼
L1  regex semantic_router（子句切分、參數抽取）       ← 現有，與 Embedding 互補
    │
    ▼
L2  ingress_router LLM（低信心兜底）
    │
    ▼
Planner LLM → Executor → Replan（主幹不變）
```

### 4.2 可能做法：強制輸出思考過程（Chain-of-Thought）

**概念**：在結構化 JSON 輸出中，**強制**模型先寫出簡短、可稽核的推理步驟，再給最終欄位（`task_type`、`tier_h`、`labels` 等）。思考過程用於除錯、回歸測試與稽核，**預設不直接顯示給使用者**（風險卡仍用 `explanation` / `safety_summary`）。

#### 為何對本專案有幫助

| 痛點 | CoT 如何緩解 |
|------|----------------|
| 元問題誤觸 `search_web` | 模型需先判斷「是否在問助理行為」再選 task_type |
| DAI 語意層過度抬分 | 強制對照 `component_scores` 與機器證據門控後才寫 tier |
| labels 與分數不一致 | 推理中須引用正文 quote，與 `quotes` 欄位對齊 |
| 除錯困難 | `pipeline_progress` / audit log 可記錄 `reasoning` |

#### 建議輸出格式（JSON 內嵌，非自由文字）

與現有 `format="json"` + `extract_json_object` 相容：思考欄位與結果欄位**同一個 JSON 物件**。

**CAI Ingress Router 範例：**

```json
{
  "reasoning_steps": [
    "句中含「搜尋」但主語是助理行為（你怎麼在搜尋）→ meta_question",
    "無待審 URL／正文 → requires_dai=false",
    "結論：direct_response，不排工具"
  ],
  "task_type": "direct_response",
  "requires_dai": false,
  "artifact_role": "none",
  "confidence": 0.88,
  "reason": "meta_question_about_assistant"
}
```

**DAI semantic_llm 範例：**

```json
{
  "reasoning_h": "命中政府補助話術框架；正文有「補助」但無匯款指令 → tier_h 上限 12",
  "reasoning_i": "無繁簡混用、錯字群聚 → tier_i=0",
  "reasoning_gate": "r_rules=15，未達 Tier1/2 門控，r_llm_optional 不得超過 20",
  "tier_h": 10,
  "tier_i": 0,
  "r_llm_optional": 10,
  "labels": ["suspicious_notification"],
  "explanation": "…",
  "safety_summary": "…",
  "quotes": [{"tier": "H", "text": "…"}]
}
```

#### Prompt 要點

1. **順序約束**：「先填 `reasoning_*`，再填分數與 labels；分數須與推理一致」。
2. **字數上限**：每步 ≤ 40 字，總推理 ≤ 200 字，避免 latency 暴增。
3. **禁止捏造**：推理不得引用 `missing_evidence` 中尚未檢測的項目（沿用 semantic_llm 現有規則）。
4. **與護欄連動**：程式端可驗證——若 `reasoning_gate` 提到機器分低但 `r_llm_optional` 高，則 cap 或標記 `reasoning_inconsistent`。

#### 程式整合（建議）

| 步驟 | 位置 | 說明 |
|------|------|------|
| 擴充 schema | `ingress_router/schemas.py`、semantic 回傳 dict | 新增 `reasoning_steps` / `reasoning_h` 等可選欄位 |
| 解析 | `llm_json.py` | 無需改動；`extract_json_object` 已支援多欄位物件 |
| 稽核 | `pipeline_progress.py`、risk `report` | 寫入 `debug.reasoning`（內部用） |
| 使用者可見 | `enrich_report_display_fields` | **不**把 raw reasoning 進風險卡 |
| 回歸 | Phase 0 黃金集 | 可對 `reasoning_steps` 做關鍵字斷言（如須含「meta_question」） |

#### 優缺點

| 優點 | 缺點 |
|------|------|
| 可稽核、利於回歸與人工複核 | token 與延遲增加（約 +15–30%） |
| 常提升意圖／標籤準確率 | 小模型（如 qwen2.5:3b）可能推理與 JSON 欄位不一致 |
| 與現有 JSON 管線相容 | 需防思考內容誤流入使用者 UI |
| 可作為 ML 特徵（推理長度、是否提及匯款等） | 非萬能；L0 規則仍不可省略 |

#### 適用階段與優先序

| 優先套用 | 原因 |
|----------|------|
| **Ingress Router L1** | 元問題、複合句邊界案例多，推理可顯著減少誤觸 |
| **semantic_llm** | 需對照機器分與話術框架，推理與 rubric 對齊 |
| Planner LLM | 次優先；已有 semantic_router 規則覆寫，成本高 |

**不建議**：對 deterministic `semantic_router`（純 regex）強制 CoT——該層應維持可預測、零 token。

#### 環境開關（建議）

```
CAI_INGRESS_COT=1          # Ingress Router 輸出 reasoning_steps
DAI_SEMANTIC_COT=1           # semantic_llm 輸出 reasoning_h/i/gate
DAI_SEMANTIC_COT_AUDIT=1     # 寫入 report.debug（預設開發／審計用）
```

### 4.3 可能做法：Embedding 向量比對（Semantic Router 第一道語意防線）

**概念**：以**預先維護的範例句庫**為每種意圖／工具建立 embedding，使用者輸入（或子句）向量化後做 cosine 相似度比對，**只決定要呼叫哪個 skill（或不必呼叫工具）**；參數（地點、URL、query）仍由 regex 抽取。若與所有範例的相似度皆不足，**預設歸為閒聊／一般對話**（`direct_response`，`todos=[]`），避免誤觸 `search_web` 等工具。

此層定位為 **L0.5**：在 Ingress L0 安全規則之後、regex `semantic_router` 與 Ingress LLM 之前，作為第一道**語意**防線。

#### 設計原則

| 原則 | 說明 |
|------|------|
| **只判 skill 類型** | Embedding 輸出 `weather` / `search_web` / `open_url_readonly` / `fetch_url` / `call_dai` / `direct_response` 等，**不**直接產生 `args` |
| **範例句驅動** | 每類意圖維護多條代表句；新增口語變體以**加範例**為主，少寫 regex |
| **無匹配即閒聊** | 最高相似度低於下限，或與次高意圖 margin 不足 → `direct_response`（不排工具） |
| **複合句先切子句** | 沿用 `split_clauses`；每子句獨立比對，再組 `todos` |
| **可關閉** | `CAI_EMBED_ROUTER=0` 時行為與現今完全一致 |

#### 意圖類別與 skill 對照（建議）

| 意圖 ID | 對應 skill | 範例句（示意） | 未命中參數時 |
|---------|----------|----------------|--------------|
| `weather` | `weather` | 「查台北天氣」「高雄會下雨嗎」 | regex 抽不到地點 → 降級 regex／LLM |
| `search_web` | `search_web` | 「搜尋台積電股價」「用 Google 查 Python」 | 抽不到 query → 降級 |
| `open_url` | `open_url_readonly` | 「打開 github」「開啟 https://…」 | 抽不到 URL → 降級 |
| `fetch_url` | `fetch_url` | 「讀這個網頁幫我摘要」 | 需正文含 URL |
| `review` | `call_dai` | 「這是不是詐騙」「連結安不安全」 | L0 送審規則仍優先 |
| `meta_question` | —（`direct_response`） | 「你怎麼在搜尋」「你可以幫我什麼」 | 與 `search_web` 範例**分開維護** |
| `direct_response` | —（`direct_response`） | 「你好」「謝謝」「介紹一下英雄聯盟」 | 閒聊、寒暄、一般短答 |
| **（無匹配）** | —（`direct_response`） | 任意未接近任何範例的輸入 | **預設閒聊，不排工具** |

#### 比對邏輯（建議）

```
1. embed(子句) → 向量 v
2. 對每個意圖類別，取與該類所有範例向量的 max cosine → scores[intent]
3. best_intent, best_sim = argmax(scores)；second_sim = 次高
4. margin = best_sim - second_sim

若 best_sim ≥ HIGH_THRESH 且 margin ≥ MARGIN_THRESH：
    → confidence=high，採用 best_intent 對應 skill（或 direct_response）
若 best_sim < LOW_FLOOR：
    → confidence=high，direct_response（embed_fallback_chat）
否則：
    → confidence=low，交 L1 regex 或 L2 LLM
```

建議初始閾值（Phase 0 黃金集調參）：

| 參數 | 建議值 | 說明 |
|------|--------|------|
| `HIGH_THRESH` | 0.82–0.88 | 高信心命中 |
| `MARGIN_THRESH` | 0.05–0.08 | 避免「搜尋」與「元問題」兩類同分 |
| `LOW_FLOOR` | 0.55–0.65 | 低於此視為與任何工具／意圖皆不相干 → 閒聊 |

#### 範例句庫（建議路徑與格式）

```
data/intent_router/exemplars.json      # 意圖定義 + 範例句（人可編輯）
data/intent_router/chroma/             # 可選：預向量化 Chroma（複用 toxic_chroma 模式）
```

```json
{
  "intents": [
    {
      "id": "weather",
      "skill": "weather",
      "exemplars": ["查台北天氣", "高雄明天會下雨嗎", "台中氣溫多少"]
    },
    {
      "id": "meta_question",
      "skill": null,
      "task_type": "direct_response",
      "exemplars": ["你怎麼在搜尋網頁", "你可以幫我處理什麼", "你是誰"]
    },
    {
      "id": "direct_response",
      "skill": null,
      "task_type": "direct_response",
      "exemplars": ["你好", "謝謝", "介紹一下英雄聯盟", "好吧"]
    }
```

範例向量於啟動時或 build 階段**預先計算**；執行期僅 embed 使用者子句一次（可參考 `dual_agent/dai/toxic_chroma.py` 的 `OllamaEmbeddings` + Chroma 模式）。

#### 與現有層級的協作

| 情境 | 行為 |
|------|------|
| Ingress L0 已判定送審／phishing | **不**進 Embedding 覆寫 |
| Embedding → `weather` + 高信心 | regex `_extract_weather_location` 抽 `location` |
| Embedding → `direct_response` | `task_type=direct_response`，`todos=[]` |
| Embedding → 無匹配（低於 LOW_FLOOR） | **閒聊**：同上，減少誤觸工具 |
| Embedding confidence=low | 交 L1 regex；仍 low 再交 L2 LLM |
| 複合句中某子句為閒聊 filler | 跳過該子句，其餘子句組 todos |

#### 稽核欄位（建議寫入 pipeline / audit）

```json
{
  "embed_router": {
    "intent_id": "weather",
    "skill": "weather",
    "similarity": 0.91,
    "margin": 0.12,
    "matched_exemplar": "查台北天氣",
    "confidence": "high",
    "reason_code": "embed_intent_match"
  }
}
```

#### 優缺點

| 優點 | 缺點 |
|------|------|
| 口語變體覆蓋優於純 regex | 每輪一次 embed 延遲（約 50–200ms） |
| 「無匹配→閒聊」可壓低誤觸工具率 | 閾值需黃金集調參 |
| 範例可持續擴充，維護成本低 | 仍依賴 embedding 模型品質 |
| 專案已有 Chroma + OllamaEmbeddings | 元問題須有獨立範例類，避免與 search 混淆 |
| 與 CoT（§4.2）可並行：Embed 定類、CoT 在 LLM 層補推理 | 不取代 L0 安全規則與參數抽取 |

#### 環境開關（建議）

```
CAI_EMBED_ROUTER=1
CAI_EMBED_EXEMPLARS_PATH=data/intent_router/exemplars.json
CAI_EMBED_HIGH_THRESH=0.85
CAI_EMBED_MARGIN=0.06
CAI_EMBED_LOW_FLOOR=0.60
```

#### 適用階段

| 階段 | 內容 |
|------|------|
| Phase 0 | 範例句庫 v1、regex vs embed 對照審計、閾值調參 |
| Phase 1 | 接入 `semantic_router`（L0.5）、`embed_fallback_chat` 行為 |
| Phase 3 | 與共用 taxonomy、多輪指代銜接 |

**不建議**：用 Embedding 取代 DAI 固定 DAG；DAI 風險管線維持規則 + 語意補充，不走 agent 自由 react。

### 4.4 可能做法：文本層面增強（Text-level Enhancement）+ KEA / TAPE → 再嵌入

**概念**：在將簡訊／通知正文轉成**深度句向量**之前，先在背景呼叫 LLM 做 **KEA（Knowledge Enhancement，知識增強）** 或 **TAPE（Threat Analysis Pattern Explanation，威脅模式解釋）**，把解讀結果與**原文拼接**後再 embedding。讓向量不只編碼字面，還編碼「已解讀的風險語意」，以提升相似度比對與下游融合的準確度。

此做法主要服務 **DAI 風險管線**（與 §4.3 CAI 意圖範例比對互補）：§4.3 用範例句定「使用者要做什麼」；本節用增強文本定「這則訊息有多危險、屬哪類話術」。

#### KEA 與 TAPE 在本計畫的定義

| 模組 | 職責 | 輸出示例 |
|------|------|----------|
| **KEA** | 從原文**抽取與補全結構化知識**（實體、關鍵片語、意圖假設） | 可疑 URL 實體、冒充機構、是否疑似假冒親友、匯款／OTP 壓力片語 |
| **TAPE** | 在 KEA 基礎上**產生可稽核的威脅解釋與模式標籤** | 「正文要求點擊短連結且聲稱帳戶異常 → 釣魚＋緊迫」；供風險卡與 audit 使用 |

兩者可**合併為一次 LLM JSON 呼叫**（建議），避免 KEA、TAPE 各打一次模型。

#### 建議管線位置（DAI DAG 內）

```
原文 text + 機器層初步結果（rules 命中、URL 列表…）
    │
    ▼
【背景】LLM KEA / TAPE（不阻塞規則層；可與 TI/TLS 並行）
    │   輸出：entities[], keyphrases[], intent_hypotheses[],
    │         patterns[], tape_summary, labels（結構化）
    ▼
文本增強（Text Augmentation）
    │   enhanced_text = 原文 + 【KEA】… + 【TAPE】…（固定模板拼接）
    ▼
深度句嵌入（OllamaEmbeddings / bge-m3 等）
    │   v_raw = embed(原文)          ← 可選保留，作對照
    │   v_enh  = embed(enhanced_text) ← 主通道
    ▼
向量證據層
    │   max_cosine vs 詐騙話術原型庫（Chroma，類 toxic_chroma）
    │   max_cosine vs 正常簡訊原型庫（壓低誤報）
    ▼
融合層（verdict）
    │   r_embed_enhanced、KEA/TAPE 結構化分項、既有 r_rules / r_toxic…
    │   **規則底線不變**（Tier 90、hard guard）
    ▼
risk_score + display_text（TAPE 摘要可進風險卡說明）
```

與現有 `semantic_supplement` 的關係：

| 現況 | 增強後 |
|------|--------|
| `semantic_llm` 在機器分項之後補 H/I | 可升級為 **KEA+TAPE 一體**，或拆成 `kea_llm` → embed → `tape` 沿用同一 JSON |
| `toxic_chroma` 對**原文**做毒樣相似度 | 新增 `scam_semantic_chroma` 對 **enhanced_text** 比對話術原型 |
| `feature_extractor` + LR | KEA/TAPE 欄位 + `v_enh` 相似度可**取代**大量 one-hot；見 §7.3 |

#### KEA 任務示例（LLM prompt 方向）

1. **意圖解讀**：「這則簡訊是否有假冒親友／政府／銀行的意圖？」→ `intent_hypotheses[]` + `confidence`
2. **實體抽取**：可疑連結、電話、金額、驗證碼、機構名 → `entities[]`（`text` 須為原文子字串）
3. **關鍵片語**：詐騙話術片段 → `keyphrases[]` + quote
4. **與機器層對齊**：已命中 `rules` 時 KEA **不得否定**；`missing_evidence` 不得假裝已檢測 TI/TLS

#### TAPE 任務示例

- 一句話 `tape_summary`（繁中，≤120 字，給分析師／風險卡）
- `patterns[]`：如 `impersonation_family`、`payment_pressure`、`credential_harvesting`
- `relations[]`（可選）：`{ "type": "impersonates", "value": "兒子", "evidence": "…" }`
- **不直接輸出最終 `risk_score`**（對齊「LLM 非主評分」原則）

#### 增強文本拼接模板（供 embedding）

```
【原文】
{raw_text}

【KEA 摘要】
實體：{entities_flat}
關鍵片語：{keyphrases_flat}
意圖假設：{intent_hypotheses_flat}

【TAPE 解釋】
{tape_summary}
模式：{patterns_joined}
```

僅 `enhanced_text` 送入深度句嵌入；原文 embedding 可選作 ablation 對照。

#### 為何能提升準確度

| 機制 | 說明 |
|------|------|
| 語意顯式化 | 「媽媽手機壞了匯款」字面與正常簡訊相近，增強後帶上「假冒親友＋匯款」語意，向量更接近詐騙原型 |
| 實體結構化 | URL／短連結實體寫入增強文本，嵌入比對不只靠 raw URL 字串 |
| 與規則互補 | 規則命中 KEA 可複述進增強文本，嵌入與融合層**同向放大** |
| 可回歸 | Phase 0 可對照 `embed(raw)` vs `embed(enhanced)` 的 AUC／誤報率 |

#### 建議輸出 JSON（單次 LLM）

```json
{
  "entities": [
    {"type": "url", "text": "https://bit.ly/xx", "span_start": 42, "span_end": 60}
  ],
  "keyphrases": ["帳戶異常", "立即驗證"],
  "intent_hypotheses": [
    {"intent": "impersonation_family", "confidence": 0.72, "evidence": "兒子說手機壞了"}
  ],
  "patterns": ["phishing", "urgency_pressure"],
  "tape_summary": "訊息聲稱親友急需匯款並附短連結，具假冒親友與緊迫匯款特徵。",
  "labels": ["impersonation", "payment_pressure"]
}
```

程式端：校驗 `entities[].text` 為原文子字串；`span` 不符則丟棄該實體。

#### 與 ML 校準路線的關係（雙路線定案，見 §1.1）

| 路線 | 說明 |
|------|------|
| **Route B（LLM）** | 本節 KEA/TAPE + 增強嵌入 + 規則融合；`DAI_RISK_FUSION_MODE=enhanced_embed` |
| **Route C（ML）** | **維持原計畫**；標註後 LR/RF；可消費 Route B 的 KEA/TAPE／嵌入特徵 |
| **並行** | shadow 對照；**不刪** `ml_lr`／`train_risk_lr.py`；`legacy` 可回退 |
| **禁止** | LLM 直接輸出最終 0–100 分取代整條管線 |

#### 優缺點

| 優點 | 缺點 |
|------|------|
| 顯著改善字面相似、語意隱晦的詐騙句 | 每則至少 1× LLM + 1× embed，延遲增加 |
| TAPE 直接支援風險卡「人話解釋」 | LLM 幻覺需 quote／span 護欄 |
| 可與 `toxic_chroma` 模式複用 | 增強文本過長可能稀釋嵌入；需模板與長度上限 |
| 比純 one-hot ML 更貼近非結構化中文 | 需詐騙／正常**雙邊**原型庫，避免單邊抬分 |

#### 環境開關（建議）

```
DAI_TEXT_ENHANCE=1              # 啟用 KEA/TAPE 文本增強
DAI_KEA_TAPE_MODE=unified       # unified | kea_only | tape_only
DAI_EMBED_ENHANCED_TEXT=1       # 對 enhanced_text 做嵌入（主通道）
DAI_SCAM_PROTOTYPE_CHROMA_DIR=… # 話術原型向量庫
DAI_EMBED_MODEL=…               # 深度句嵌入模型（可與 toxic 共用端點）
```

#### 適用階段

| 階段 | 內容 |
|------|------|
| Phase 0 | `embed(raw)` vs `embed(enhanced)` 對照集；KEA 實體 span 準確率 |
| Phase 2 | `kea_tape_llm.py`、增強拼接、`scam_prototype_chroma`、接入 `verdict` |
| Phase 3 | TAPE 摘要進風險卡；與 ML 計畫文件對齊修訂 |

**背景執行**：KEA/TAPE 宜在 `build_analysis_payload` 之後、`semantic_supplement` 同級或之前啟動 async；機器規則層**先跑、不等待** LLM，但融合層在語意分項齊備後再算最終分（與現有 DAG 步驟順序一致）。

## 六、Phase 1：CAI 意圖路由改善

**目標**：減少 Planner LLM 誤排工具；高信心規則覆蓋常見任務句型。

### 6.1 L0/L1 Ingress 強化

| 工作項 | 做法 |
|--------|------|
| 元問題／能力詢問短路 | 擴充 `meta_assistant_or_chat_scope` 模式；Ingress 與 validate **同一套** taxonomy |

### 6.2 Semantic Router v2（規則層）

| 工作項 | 做法 |
|--------|------|
| 子句切分 | 擴充連接詞（「還有」「另外」「順道」）；支援全形／半形 |
| skill 覆蓋 | 補 `instant_answer` 觸發（「是什麼」「幾點」「多少」+ 實體） |

### 6.2b Semantic Router v2.5（Embedding 意圖層，§4.3）

| 工作項 | 做法 |
|--------|------|
| 範例句庫 | `data/intent_router/exemplars.json`；含工具意圖 + `meta_question` + `direct_response` |
| 比對模組 | `dual_agent/cai/embed_intent_router.py`（複用 `OllamaEmbeddings`／Chroma 模式） |
| 只判 skill | 命中後交現有 regex 抽 `location`／`url`／`query` |
| **無匹配→閒聊** | `best_sim < LOW_FLOOR` → `direct_response`，`reason_code=embed_fallback_chat` |
| 與 regex 協作 | embed `confidence=low` 時 fallback L1 regex；預設 `CAI_EMBED_ROUTER=0` |
| 稽核 | 記錄 `intent_id`、`similarity`、`matched_exemplar` 至 pipeline progress |

## 七、Phase 2：DAI 語意層改善

**目標**：語意層**可稽核、可回歸**；在機器證據不足時不過度抬分。

### 7.1 結構化輸出與護欄

| 工作項 | 做法 |
|--------|------|

### 7.2 Prompt 與話術庫

| 工作項 | 做法 |
|--------|------|
| 台灣詐騙框架 H | 按類別維護話術範例（政府補助、物流、銀行、投資、OTP）嵌入 few-shot |
| 語言品質 I | 繁簡混用、錯字群聚的明確評分 rubric（0 / 4 / 8 / 12） |
| 版本化 | `SEMANTIC_PROMPT_VERSION` 環境變數；變更 prompt 須更新回歸集預期 |
| **強制思考過程** | `reasoning_h` / `reasoning_i` / `reasoning_gate`（§4.2）；推理與分數不一致時程式 cap |

### 7.2b 文本層面增強（KEA / TAPE → 增強嵌入，§4.4）

| 工作項 | 做法 |
|--------|------|
| KEA/TAPE 統一 LLM | `dual_agent/dai/risk_analysis/kea_tape_llm.py`；一次 JSON 輸出實體、意圖假設、patterns、`tape_summary` |
| 文本拼接 | `build_enhanced_text(raw, kea_tape)` 固定模板；長度上限（如 ≤ 800 字） |
| 深度句嵌入 | `embed(enhanced_text)` 為主；可選保留 `embed(raw)` 作 ablation |
| 話術原型庫 | `data/scam_prototypes/` + Chroma collection（政府補助、假冒親友、釣魚連結…） |
| 融合掛點 | `verdict.py` 新增 `r_embed_enhanced`；與 `r_toxic_fused`、KEA patterns 加權 |
| 風險卡 | `tape_summary` 併入 `safety_summary` 或 `display_text` 補充段 |
| 護欄 | 實體 `text` 須為原文子字串；LLM **不**輸出最終 `risk_score` |

**示例場景（驗收用）**：

- 「媽媽我手機壞了先匯款」→ KEA：`impersonation_family`；TAPE：假冒親友＋匯款壓力
- 含 `bit.ly` 短連結＋銀行異常文案 → KEA：提取 URL 實體；增強嵌入靠近釣魚原型

### 7.3 與 ML / 嵌入融合路線銜接

對齊 [DAI_ML風險校準.md](./DAI_ML風險校準.md)，並納入 §4.4 文本增強路線：

| 工作項 | 做法 |
|--------|------|
| labels → 特徵 | KEA/TAPE 的 `patterns`、`entities` 進 `feature_extractor`（或取代部分 lbl_*） |
| 嵌入特徵 | `embed_enhanced_max_cosine`、`embed_raw_max_cosine` 作連續特徵 |
| 融合模式 | 新增 `DAI_RISK_FUSION_MODE=enhanced_embed`；與 `legacy`／`ml_lr` shadow 對照 |
| 雙模式切換 | `enhanced_embed` 模式下統一融合入口，避免 `semantic_floor` 與嵌入雙重抬分 |
| 訓練資料 | replay 產出增強文本 + 嵌入特徵；併入 bootstrap 資料集 |

### 7.4 驗收標準

- [ ] DAI 語意回歸集：label 命中率 ≥ **85%**（允許邊界案例人工標記）

## 八、Phase 3：跨層整合與長期演進

**目標**：CAI 意圖與 DAI 語意共用 taxonomy；端到端可追蹤。

### 8.1 共用意圖／風險 taxonomy

| 概念 | CAI | DAI |
|------|-----|-----|
| `check` / 送審 | Ingress、`call_dai` | 完整 DAG |
| `hypothetical_risk` | `direct_response` + 可選輕量 DAI | 簡化評分路徑（未來） |
| `malicious_link` 等 label | Planner 不開連結 | 阻擋／追問建議 |

建立 `dual_agent/shared/intent_risk_taxonomy.py`（或擴充 `task_taxonomy`），Ingress、semantic_router、semantic_llm 引用同一枚舉。

### 8.2 指代與多輪上下文

- CAI：`deictic_needs_context` → Memory 提供上一輪 artifact／URL
- DAI：送審正文與使用者追問分離存入 `payload`，語意層只看 artifact

### 8.3 Threat Intel / TLS 接入後重平衡

TI/TLS 上線後重新跑 Phase 0 基線，**下調** `DAI_R_LLM_WEIGHT` 預設值（語意層不再補機器缺口）。

### 8.4 驗收標準

- [ ] 端到端劇本（`agent_full_coverage`）全綠
- [ ] ML LR 模型（若 Phase 1 完成）validation AUC ≥ 基線 + **0.05**
- [ ] 風險卡 `explanation` 使用者可讀性人工抽樣滿意度 ≥ **80%**
